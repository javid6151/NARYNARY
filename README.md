# Zipnary — PG & Hostel Management (ZIPCO Solutions)

Multi-tenant PG / hostel management SaaS built from the specs in [`docs/`](docs) and the rules in [`AGENTS.md`](AGENTS.md).

- **Frontend:** Vite + React 19 + TypeScript + Tailwind v4 (one app, five portals)
- **Backend:** Supabase — Postgres with Row-Level Security on every tenant table, Auth, and `security definer` SQL functions (RPC) for every multi-row / privileged workflow
- **Brand name** is configurable via `VITE_BRAND_NAME` (default “ZIPNARY”); plan pricing/limits live in the database and are edited by the platform admin.

## Portals

| Route | Who | What |
|---|---|---|
| `/platform` | ZIPCO Platform Super Admin | Onboarding approvals, building approvals, tenant suspend/reactivate, subscriptions & limits, plans, audit log |
| `/app` | PG Owner, Managers (assigned buildings only) | Dashboard, buildings/floors/rooms/beds (interactive floor layout), residents, admissions (5-step wizard + owner approval), payments (dues, collections, receipts, reversals, monthly rent generation), expenses + vendors, complaints, maintenance (requests, status workflow, linked costs), food/mess (live headcount, weekly planner, last-minute changes with resident notification, reviews), inventory (store ↔ kitchen ledger), staff (roster, attendance, daily reports, salaries), communication (building/floor/room chats, notices), reports (CSV/print), settings (team invites, meal cutoffs, categories) |
| `/kitchen` | Chef (assigned buildings) | Today’s headcount per meal, who’s not eating, record ingredients used / returned / wasted, issue stock, menu, history. No access to resident KYC or finance. |
| `/resident` | Resident | Dues & receipts, mark meals unavailable before cutoff, rate meals, complaints, notices, community chat, profile |

## Run locally

Prerequisites: Node 20+, Docker Desktop running.

```bash
npm install
npm run db:start        # local Supabase in Docker (first run downloads images)
npm run db:reset        # applies supabase/migrations + seed.sql
npm run seed:dev        # creates test users and data by calling the real RPC workflows
npx supabase status     # copy API URL + anon key into .env.local (see .env.example)
npm run dev             # http://localhost:5173
```

## Checks

```bash
npm run build      # type-check + production build
npm run lint
npm test           # unit tests (vitest)
npm run test:rls   # 49 security/integrity tests against the local stack (run after seed:dev)
npm run db:types   # regenerate src/lib/database.types.ts after any migration (needs db:start)
```

`test:rls` covers: cross-tenant reads/writes with manipulated IDs, manager building scope, chef restrictions (no KYC/finance/salary), resident privacy, anonymous access, two concurrent admissions on one bed, concurrent approval, idempotent payment and inventory retries, over-allocation, negative stock, capacity below occupancy, platform-only functions, and suspension cutting off access. It changes a little data, so run `npm run db:reset && npm run seed:dev` afterwards for a clean demo.

## Project structure (`src/`)

```text
src/
  main.tsx                 entry: router + AuthProvider
  app/                     composition only
    App.tsx                route table for all portals (lazy-loaded)
    Gate.tsx               route guard (session + role) and full-page loader
    StaffShell.tsx         owner/manager layout (sidebar, header)
  lib/                     framework glue, no domain knowledge
    supabase.ts            typed Supabase client (anon key only)
    database.types.ts      GENERATED by `npm run db:types` — do not edit
    api.ts                 rpc() (function + argument names type-checked), q(), ApiError, newKey()
    hooks.ts               useAsync / useMutation (loading, error, double-submit guard)
    format.ts, validation.ts, cx.ts, brand.ts
  components/              domain-free UI kit (ui.tsx, Charts, Logo, BuildingPicker)
  features/<domain>/       one folder per business area
    api.ts                 every query/RPC for the domain, with a doc comment
    types.ts               row shapes the UI works with
    <Page>.tsx             routed page(s)
    components/            drawers, dialogs, tables used by the pages
```

Domains: `access` (session, memberships, selected building), `auth`, `onboarding`, `dashboard`, `property`,
`residents` (incl. the `new-admission/` wizard steps), `billing`, `expenses`, `maintenance` (complaints + requests),
`kitchen` (owner Food/Inventory and the `chef/` portal), `staff`, `communication` (notices, chat, notifications),
`files` (private uploads), `reports`, `settings`, `audit`, `resident-portal`, `platform`.

Rules of thumb:

- Components never query the database directly — they call functions from their feature's `api.ts`
  (the only `supabase` use in a component is `AuthProvider` managing the auth session).
- Writes go through RPCs; `rpc('name', { p_arg })` is checked against the generated types, so a renamed SQL function
  or parameter fails the build. Run `npm run db:types` after changing a migration.
- jsonb RPC results and database views (which Postgres reports as all-nullable) are the only places a shape is
  asserted with a cast, and each cast lives in an `api.ts` next to a comment.
- A page imports from its own feature, `components/`, `lib/`, and other features' `api.ts`/`components/` — never from
  another page file.

## How access works

- Roles come only from `tenant_memberships` / `building_memberships` / `platform_admins` — never from the client.
- **Owners** sign up and submit onboarding; nothing operational is available until a platform admin approves.
- **Managers/chefs** are invited by email from Settings → Team (limits come from the subscription); they sign up with that email and access is granted after email verification.
- **Residents** get access only after the owner approves their admission; they sign up with the email on their record. No passwords are generated or sent — the WhatsApp button only shares the signup link and instructions.

## Database layout (`supabase/migrations`)

1. Identity, tenants, memberships, onboarding, subscriptions, audit, RLS helpers
2. Buildings, floors, rooms, beds (+ building-scoped access helper)
3. Residents, admissions, bed assignments (partial unique indexes: one occupant per bed), documents, checkouts
4. Rent charges, payments, allocations, receipts, expense ledger, vendors, balance views
5. Complaints, maintenance requests and activity
6. Meal menus/availability/reviews, inventory locations/items/immutable transaction ledger, kitchen reports
7. Staff roster/attendance/daily reports, notices, notifications, chat
8–9. Workflow RPCs (onboarding, approvals, admissions, checkout, payments, expenses, salaries, maintenance, meals, inventory, chat, dashboard)
10. Privilege hardening (anon has nothing; authenticated gets SELECT + narrow column grants; writes via RPC)
11. Resident self-profile RPC · 12. Explicit tenant-safe composite foreign keys
13. Private storage buckets (`resident-documents`, `expense-invoices`, `maintenance-attachments`; 5 MB, PDF/JPG/PNG/WEBP), attachment tables, `begin_upload` → upload → `complete_upload`, KYC verify/reject. `storage.objects` policies authorize by the owning record, never by path; files open via 60-second signed URLs
14. Human-readable, permanent tenant code (`ZPN-000001`) assigned by the database to every hostel business. Full schema reference: [`docs/database-structure.md`](docs/database-structure.md)
15. Resident community: lost & found / marketplace / suggestion / feedback posts, staff polls (one vote per resident), visitor passes with gate codes, chat unread tracking, opt-in birthdays

## Known limitations / not yet built

- No online payment gateway: payments are recorded by the PG (cash/UPI/bank/card). Gateway + webhooks need a separate design.
- File uploads: residents cannot upload their own documents yet (staff upload on their behalf). Abandoned upload slots (`uploaded_at is null`) are hidden but not yet cleaned up by a job; files are never deleted (documents are rejected instead). Content is checked by declared type/size only — no virus scanning.
- Email/WhatsApp delivery uses in-app notifications plus a WhatsApp click-to-chat link; there is no outbox/provider integration yet.
- Exports are CSV (opens in Excel) and browser print-to-PDF; no server-side XLSX/PDF generation.
- Chat refreshes by polling every 8 s rather than Supabase Realtime.
- Recurring maintenance schedules and staff multi-shift attendance are not implemented.
- Rent is billed by calendar month (first month pro-rated). Late fees are added manually.
